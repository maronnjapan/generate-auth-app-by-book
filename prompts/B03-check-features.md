# B.3 既存の実装に含まれる機能の確認

`[ ]` を、確認したい機能に書き換えてから渡してください。
書き換えずに渡した場合は、本書の例（2.6.2）と同じく PKCE を確認します。

---

## 目的

気になった機能が、今の実装にすでに入っているかを知りたい。
入っているなら実装箇所と設定を、入っていないなら追加するときに変更が必要になる箇所を知りたい。

## 確認したい機能

[PKCE（RFC 7636 Proof Key for Code Exchange）]

## 対象

- `chapter2/openid-provider/`（OpenID Provider。以下 OP）
- `chapter2/app-a/`、`chapter2/app-b/`（Web アプリ）

## 依頼

コードは変更しないでください。読んで報告するだけにしてください。

### 1. 確認したい機能の有無

OP とアプリのそれぞれについて、機能に必要な処理があるかを調べ、根拠となるファイルと行番号を示してください。
PKCE の場合は、次の項目を調べます。

- OP の認可エンドポイントが `code_challenge` と `code_challenge_method` を受け取り、認可コードと一緒に保存しているか
- OP のトークンエンドポイントが `code_verifier` を受け取り、保存した `code_challenge` と照合しているか
- OP が `code_challenge` の無い認可リクエストをどう扱うか（受け付ける、拒否する、設定で切り替える）
- アプリが `code_verifier` を生成して保存し、認可リクエストに `code_challenge` を付け、トークンリクエストに `code_verifier` を付けているか
- Discovery に `code_challenge_methods_supported` があるか
- 機能を切り替える設定（環境変数など）があるか

別の機能を確認する場合は、その機能の仕様が求める処理を同じ粒度で列挙してから調べてください。

### 2. 一緒に把握しておく項目

次の項目も表にまとめてください。機能を追加するときの影響範囲を知るためです。

- クライアント認証: トークンエンドポイントが受け付ける方式（`client_secret_post`、`client_secret_basic`、なし）
- 認可コード: 一回限りか、有効期限、`redirect_uri` と `client_id` の一致確認、保存場所
- `state` と `nonce`: アプリ側の生成、保存、検証の有無。OP 側の `nonce` の扱い
- セッション: OP とアプリそれぞれの Cookie の名前と属性（HttpOnly、SameSite、Secure）
- ID トークン: 署名アルゴリズム、含まれるクレーム、アプリ側で検証している項目
- 依頼していないのに実装されている機能、依頼したのに省かれている機能

## 出力

- 表（項目、現在の実装、根拠のファイル:行、備考）
- 確認したい機能についての結論を一言で（「実装済み」「一部だけ実装」「未実装」のどれか）
- 実装済みの場合: 動きを確かめる方法（`curl` の例やブラウザーでの操作）と、関係する設定
- 未実装、または一部だけ実装の場合: 追加するときに変更が必要になる箇所の一覧（ファイルと関数名）

## 守ること

- 推測で書かない。コードで確認できないことは「不明」と書く
- 回答は日本語で書く
